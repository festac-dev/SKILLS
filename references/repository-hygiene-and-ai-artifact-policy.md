# Repository Hygiene and AI Artifact Policy

## Objective
Keep the delivered project professional, intentional, reviewable, and free of accidental assistant chatter or local working artifacts. Treat AI-generated content like any other contribution: inspect it, edit it, test it, and retain it only when it belongs in the product.

## Keep out of shipped project content
Remove irrelevant AI/assistant self-references, including:
- "Generated by AI", "Created by ChatGPT", "As an AI language model", and similar attribution or disclaimers when not legally, contractually, or product-required.
- Assistant-to-user instructions, conversational explanations, progress updates, TODOs addressed to the user, and implementation narration.
- Prompt fragments, hidden chain-of-thought requests, tool transcripts, internal agent messages, raw chat logs, and copied planning notes.
- Placeholder claims, fabricated credentials, fake metrics, unsupported statements, and generic filler comments.
- Comments that merely narrate obvious code, repeat the implementation, or mention that AI wrote the code.

Do not remove useful technical documentation, meaningful rationale, security warnings, provenance required by policy, license notices, generated-code notices required by a tool/license, or attribution legally required by a dependency or dataset.

## Source comments and documentation
- Comments should explain non-obvious intent, constraints, invariants, trade-offs, or hazards.
- Prefer clear names and straightforward code over explanatory comment noise.
- Keep public documentation written for the actual audience, not as a conversation with an assistant.
- Do not add AI attribution by default. Preserve it where required by law, license, policy, or explicit product requirements.
- Never conceal authorship or provenance when disclosure is required.

For public README edits, [technical documentation](../specialists/technical-documentation.md#documentation-audience-and-evidence) owns audience selection and claim-to-evidence presentation. Keep personal delivery reminders and grading advice in private working notes while retaining actionable configuration, truthful simulation labels and required public disclosures.

For a hackathon application's publication, inventory internal reports and submission-planning documents as private working material. Move them outside the repository, update public callers and add narrow ignore rules for known generated names. Review already tracked files separately; ignore rules alone do not exclude them from a push. Preserve the submitted product, its evidence artifacts and required notices rather than ignoring all reports or Markdown by wildcard.

## Git hygiene
- Ignore local-only agent state, prompt scratchpads, chat transcripts, temporary plans, generated logs, caches, credentials, local databases, build output, and editor/OS noise when they are not intentional project artifacts.
- Do not blindly ignore all Markdown, comments, tests, scripts, or generated source. Some are essential project files.
- Use narrow, documented ignore patterns. Review `git status --ignored` and `git check-ignore -v <path>` when debugging.
- Keep shared agent configuration only when intentionally designed for the repository and safe for collaborators.
- Never put secrets in Git; use environment variables and an appropriate secret manager.
- Review staged files before every commit. `.gitignore` does not untrack files already committed.

## Development prompts and publication scope

Keep development prompt dumps, copied design prompts, chat transcripts, temporary recording scripts and unrelated downloaded toolkits outside the application repository, or under specific ignored paths when they remain useful locally. A request to prepare a repository for Git includes checking for this residue; it does not authorize publishing or committing.

Inspect what a file does before removing it. Runtime prompts used by the product, skill source when the toolkit is the deliverable, tests, licenses and intentional project guides can belong in Git. Avoid blanket `*.md`, `*prompt*` or entire agent-directory exclusions. Follow an explicit request to remove a named guide; a generic preserve-guides recommendation does not override it.

For each confirmed removal, check imports, scripts and documentation links, then remove or update those callers. Add narrow ignore rules if local tooling may recreate the file. Include symlinks in the inventory: unlinking an unwanted alias must not delete the guide or asset it targets. Preserve a requested exception such as a toolkit entrypoint.

## Cache cleanup by purpose

| Artifact | Default action for a cache-cleanup request |
|---|---|
| Untracked compiler output, bundler cache, test cache, bytecode | Remove after confirming its generator and checking active consumers |
| Installed dependencies, SDKs, browsers, offline model weights | Retain; these are toolchains, not automatically disposable caches |
| Databases, ledger state, uploads, identities, credentials | Preserve even when hidden, ignored or named `local` |
| Completed videos, captions, source recordings, original artwork | Preserve; intermediate render chunks are a separate category |
| Tracked generated code, vendored files or fixtures | Review as source changes; do not silently delete as caches |
| Unknown scratch directory or backup | Inspect ownership and contents before classifying |

Inspect Git status, build commands, disk use and relevant processes before deletion. A running server may still need its compiled output. Stop only task-owned producers when authorized, or skip their active paths. Never treat `git clean -fdx`, `docker system prune --volumes` or a blanket hidden-directory deletion as routine cache cleanup.

Use [cache_cleanup.py](../scripts/cache_cleanup.py) for an explicit list of inspected regenerable paths. It defaults to a JSON preview and checks root containment, tracked files, protected state, target symlinks, Linux process use and metadata changes before applying the same plan. It does not determine whether a directory's contents are reproducible, and process inspection is best effort where access is restricted.

```sh
# Select actual cache paths; keep the JSON outside every deletion target.
python /path/to/SKILLS/scripts/cache_cleanup.py --root /path/to/project \
  --path build --path node_modules/.vite > /path/to/local-work/cleanup.json

# Inspect every target. Existing cleanup authorization covers applying it.
python /path/to/SKILLS/scripts/cache_cleanup.py --root /path/to/project \
  --apply-plan /path/to/local-work/cleanup.json
```

The helper refuses whole dependencies, protected state/export paths, nested repository/database/credential markers and changed plans. Filesystem metadata is a stale-work check, not protection against a malicious concurrent writer. Keep writers stopped for the operation. An interrupted cleanup may have removed earlier entries; inspect what remains instead of replaying a stale plan. Hard-linked build artifacts can change a later target's link count when an earlier target is removed; inspect a fresh plan for the remainder instead of suppressing the metadata check. Report logical bytes removed separately from measured free space because hardlinks, compression and concurrent writes affect reclaimed storage.

## Verify the handoff

Check that deleted candidates are gone, intended source changes are the only Git changes, and retained runtime data and final outputs are unchanged. Test actual ignore rules against representative paths and check already tracked unwanted artifacts separately. For directory-only maintenance, use file inventories and hashes instead of claiming a Git review. Do not immediately rebuild solely to validate a successful cleanup and recreate the output just removed.
